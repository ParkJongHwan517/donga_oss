# CI/CD 최적화 전후 비교 리포트

FIT 저장소의 GitHub Actions를 최적화하고, 전후를 수치로 비교한 리포트입니다.
모든 수치는 이 저장소에서 실제로 실행한 기록이며, 근거가 되는 실행 링크를 [부록](#부록-근거-실행-기록)에 모았습니다.

## 1. 요약

| 최적화 | 전 | 후 | 개선 |
|---|---|---|---|
| 중복 제거 (Composite Action, Reusable Workflow) | `setup-python` 4곳에 복사 | 1곳 (Action 하나를 7곳에서 호출) | 환경 준비 로직 **−75%**, `ci.yml` **89줄 → 50줄 (−44%)** |
| Matrix 확장 | 9개 조합, 102초 | 12개 조합, 100초 | 조합 **+33%**, 소요 시간 유지 |
| pip 캐시 (통제된 벤치마크, 3회 평균) | 설치 7.7초 | 4.7초 | 설치 단계 **−39.1%**, 환경 준비 전체 **−19.2%**, 잡 전체 **−17.5%** |
| pip 캐시 (실제 CI 1회 비교) | 100초 | 93초 | 전체 **−7.0%** (설치 시간 합계 −8.2%) |
| 선택적 배포 (앱 코드 변경이 없는 경우) | 56.5초 | 14.5초 | 소요 시간 **−74.3%**, 잡 실행 시간 **−88.2%** |
| 선택적 배포 (앱 코드를 바꾼 경우) | 56.5초 | 86초 | **+52%** (악화, 원인은 6장) |

핵심 결론은 세 가지입니다.
1. 중복 제거와 선택적 배포는 효과가 분명합니다.
2. 캐시는 **효과가 있지만 작습니다.** 이 프로젝트는 의존성 설치 자체가 빠르기 때문입니다.
3. 의존성을 늘리자 코드 변경 시 파이프라인은 오히려 느려졌습니다.

## 2. 측정 방법과 한계

| 항목 | 내용 |
|---|---|
| 환경 | GitHub-hosted 러너 (ubuntu-latest, windows-latest, macos-latest) |
| 시간 측정 | 워크플로우 `run_started_at` ~ `updated_at` (소요 시간), 잡/스텝의 `started_at` ~ `completed_at` (잡 실행 시간) |
| 설치 시간 | Composite Action이 `date +%s`로 직접 잰 값 (1초 단위) |
| 캐시 벤치마크 | `Cache Benchmark` 워크플로우를 3회 실행, 같은 Python(3.12)과 의존성(46개 패키지)으로 비교 |
| 집계 | `scripts/cache_benchmark_report.py`, `scripts/ci_run_compare.py` |

**한계**
- 시간이 1초 단위라서 몇 초짜리 작업의 개선률은 오차가 큽니다. 같은 조건의 반복에서도 설치 시간이 7~8초로 흔들렸습니다.
- 러너 성능은 실행마다 달라서, 실제 CI 비교(5장)는 1회 측정이라 통계적으로 확정할 수 없습니다.
- "전" 기록 중 일부는 최적화 이전 실행(예: CI #3, 파이프라인 #2, #3)을 그대로 사용했고, 같은 조건의 재측정은 아닙니다.

## 3. 중복 제거: Composite Action과 Reusable Workflow

환경 준비(Python 설치, 캐시, 의존성 설치)와 테스트 절차를 워크플로우마다 복사해 쓰고 있었습니다.

| 구분 | 파일 |
|---|---|
| Composite Action | `.github/actions/setup-python-env/action.yml` |
| Reusable Workflow | `.github/workflows/reusable-test.yml` |

| 지표 | 전 | 후 |
|---|---|---|
| `ci.yml` 줄 수 | 89줄 | 50줄 (−44%) |
| `actions/setup-python` 호출 위치 | 4곳 (`ci.yml` 2, `pipeline.yml` 2) | 1곳 (Action 내부) |
| 환경 준비 로직 호출 방식 | 코드 복사 | `uses: ./.github/actions/setup-python-env`로 7곳에서 재사용 (`ci.yml` 1, Reusable 1, `pipeline.yml` 2, 벤치마크 3) |
| 테스트 절차 (Secrets 주입, 테스트 실행, 결과 업로드) | `ci.yml` 안에 직접 작성 | Reusable Workflow 1곳 |

규칙을 바꿀 때(예: 캐시 키, Python 설치 방식) 이제 파일 한 곳만 고치면 됩니다. 실제로 캐시 벤치마크를 만들 때 Action에 `use-cache`, `cache-key-suffix` 입력만 추가해서 같은 코드를 그대로 재사용했습니다.

참고로 `pipeline.yml`은 줄 수가 151줄에서 229줄로 늘었습니다. 중복이 늘어난 것이 아니라 6장의 변경 감지, 요약 잡이 추가되었기 때문입니다.

## 4. Matrix 확장

| 구분 | 전 (CI #3) | 후 (CI #5) |
|---|---|---|
| 조합 수 | 9개 (Ubuntu·Windows × Python 4종 + macOS 1) | **12개** (Ubuntu·Windows·macOS × Python 4종) |
| 잡 수 (Lint 포함) | 10개 | 13개 |
| 전체 소요 시간 | 102초 | **100초** |
| 잡 실행 시간 합계 | 239초 | 361초 |

조합이 33% 늘었지만 병렬로 돌아서 소요 시간은 그대로입니다. 잡 실행 시간 합계가 51% 늘어난 것은 조합 증가(+33%)와 추가된 의존성(46개 패키지) 때문입니다.

## 5. pip 캐시 전후

### 5.1 통제된 벤치마크 (같은 조건에서 3회)

`Cache Benchmark`는 한 번 실행에서 세 가지를 비교합니다.
- **no-cache**: 캐시 없이 설치 (전)
- **cache-cold**: 캐시를 쓰지만 처음이라 미스 (캐시를 만드는 비용)
- **cache-warm**: cold가 만든 캐시를 복원 (후)

**의존성 설치 단계 (pip install만)**

| 실행 | no-cache | cache-cold | cache-warm | 개선률 (warm) |
|---|---|---|---|---|
| #1 | 8초 | 8초 | 4초 | 50.0% |
| #2 | 7초 | 7초 | 6초 | 14.3% |
| #3 | 8초 | 8초 | 4초 | 50.0% |
| **평균** | **7.7초** | **7.7초** | **4.7초** | **39.1%** |

**평균 기준 비교**

| 측정 범위 | no-cache | cache-cold | cache-warm | 개선률 (warm) |
|---|---|---|---|---|
| 설치 단계 | 7.7초 | 7.7초 | 4.7초 | **39.1%** |
| 환경 준비 단계 전체 (setup-python + 캐시 복원 + 설치) | 8.7초 | 9.0초 (−3.8%) | 7.0초 | **19.2%** |
| 잡 전체 | 13.3초 | 14.0초 (−5.0%) | 11.0초 | **17.5%** |

- 설치 단계만 보면 약 39% 빠릅니다.
- 캐시를 복원하는 시간이 포함되면 개선률이 19%로 줄고, 잡 전체로는 17.5%입니다.
- **절대값으로는 잡 하나당 약 2.3초 절약**입니다.
- 캐시를 처음 만드는 cold 실행은 저장 비용 때문에 no-cache보다 약 0.7초(5%) 느립니다.

### 5.2 실제 CI에서의 효과 (12개 조합, 1회 비교)

같은 코드로 `CI`를 두 번 실행했습니다. #5는 캐시가 거의 없는 상태(13개 중 1개만 적중, 이 1개는 Lint가 만든 캐시를 같은 키의 테스트가 쓴 것), #6은 13개 모두 적중했습니다.

| 지표 | #5 (미스) | #6 (히트) | 변화 |
|---|---|---|---|
| 전체 소요 시간 | 100초 | 93초 | **−7.0%** |
| 의존성 설치 시간 합계 | 134초 | 123초 | −8.2% |
| 잡 실행 시간 합계 | 361초 | 374초 | +3.6% |

| OS | 설치 평균 (미스 → 히트) | 개선 |
|---|---|---|
| Windows | 18.2초 → 15.8초 | +13.7% |
| Ubuntu | 6.6초 → 6.0초 | +9.1% |
| macOS | 7.0초 → 7.5초 | −7.1% (악화) |

### 5.3 해석
- 캐시는 **효과가 있지만 작습니다.** 벤치마크는 17~39%, 실제 CI는 7~8%로, 절약 시간은 잡 하나당 몇 초입니다.
- 실제 CI에서 개선이 더 작은 이유는 (1) 캐시 복원·저장 오버헤드, (2) 러너 성능 편차(±몇 초), (3) 시간이 오래 걸리는 Windows가 전체 소요 시간을 결정하기 때문입니다. 잡 실행 시간 합계는 오히려 늘었으므로 이 1회 비교만으로 "캐시가 빨라졌다"고 단정할 수 없습니다.
- 개선 폭이 작은 근본 원인은 **의존성 설치가 원래 빠르기 때문**입니다. 46개 패키지도 PyPI에서 wheel을 받으면 Ubuntu 기준 6~8초입니다. 캐시가 아껴줄 수 있는 시간이 작습니다.
- 설치가 가장 느린 Windows에서는 효과가 상대적으로 뚜렷했습니다.

## 6. 선택적 배포

`pipeline.yml`을 두 가지 조건으로 제어합니다.

| 조건 | 동작 |
|---|---|
| 변경 파일 감지 | `fit/`, `tests/`, `pyproject.toml`, `requirements*.txt` 중 하나라도 바뀌면 Build/Test/Deploy 실행. 문서나 워크플로우만 바뀌면 전부 건너뜀 |
| 브랜치/PR 조건 | PR에서는 Build/Test까지만 실행하고 Deploy는 건너뜀. Deploy는 `main` 푸시나 수동 실행에서만 |

### 6.1 실행 결과

| 실행 | 이벤트 | 변경 내용 | Build | Test | Deploy | 소요 | 잡 실행 시간 |
|---|---|---|---|---|---|---|---|
| #4 | PR | 워크플로우만 | 건너뜀 | 건너뜀 | 건너뜀 | 14초 | 6초 |
| #5 | main 푸시 | 워크플로우만 | 건너뜀 | 건너뜀 | 건너뜀 | 15초 | 7초 |
| #6 | PR | 앱 코드 (`feat:`) | 성공 | 성공 | **건너뜀** | 77초 | 77초 |
| #7 | main 푸시 | 앱 코드 (`feat:`) | 성공 | 성공 | **성공 (버전 0.2.0)** | 86초 | 83초 |

네 가지 경우가 모두 의도대로 나왔습니다. 특히 같은 앱 코드 변경이라도 PR(#6)에서는 배포하지 않고, 병합 후 `main` 푸시(#7)에서만 배포했습니다.

### 6.2 전후 비교

"전"은 선택적 배포 이전의 파이프라인으로, 변경 내용과 관계없이 항상 Build/Test/Deploy를 모두 실행했습니다. (#2, #3 평균: 소요 56.5초, 잡 실행 55.0초)

| 변경 종류 | 전 | 후 | 변화 |
|---|---|---|---|
| 앱 코드 이외 (문서, 워크플로우) | 56.5초 (잡 55.0초) | **14.5초 (잡 6.5초)** | 소요 **−74.3%**, 잡 실행 **−88.2%** |
| 앱 코드 변경 | 56.5초 | 86초 (#7) | **+52% (악화)** |

### 6.3 코드 변경 시 느려진 이유
- 변경 감지(`Detect changes`)는 4초에 불과해 원인이 아닙니다.
- 5장 벤치마크를 위해 `requirements.txt`에 FastAPI, Supabase 등 46개 패키지를 추가한 뒤, `Build`와 `Test` 잡이 모두 이 의존성을 설치하게 되었습니다. 최적화 이전에는 개발 도구 3개(`pytest`, `ruff`, `build`)만 설치했습니다.
- 즉 선택적 배포 자체는 코드 변경 시 비용을 만들지 않고, **의존성 증가가 파이프라인 시간을 늘렸습니다.** 이번 최적화 전체에서 유일하게 악화된 지점입니다.
- 코드 변경이 아닌 커밋(문서, 워크플로우 수정)이 많을수록 선택적 배포의 이득이 커집니다.

## 7. 한계와 개선 방향

| 항목 | 내용 |
|---|---|
| 측정 횟수 | 실제 CI 비교는 1회, 벤치마크는 3회입니다. 횟수를 늘리고 중앙값을 쓰면 신뢰도가 올라갑니다. |
| 시간 해상도 | 1초 단위라 개선률 오차가 큽니다. |
| 캐시 방식 | 지금은 pip의 wheel 캐시를 저장합니다. 설치된 가상환경(`site-packages`)을 통째로 캐시하거나 `uv` 같은 빠른 설치 도구를 쓰면 더 큰 개선이 가능할 수 있습니다. 이번에는 측정하지 않았습니다. |
| 파이프라인 시간 | Build와 Test에서 개발용 의존성 전체를 설치합니다. 테스트에 필요한 최소 의존성만 따로 설치하면 6.3의 악화를 줄일 수 있습니다. |
| 배포 | 실제 서버가 없어서 배포 단계는 배포 폴더와 `MANIFEST.txt`를 만드는 시뮬레이션입니다. |

## 8. 재현 방법

```bash
# 캐시 벤치마크 평균과 개선률 (Cache Benchmark를 여러 번 실행한 뒤)
python scripts/cache_benchmark_report.py --repo ParkJongHwan517/donga_oss --limit 3

# 두 CI 실행의 설치 시간과 캐시 적중 비교
python scripts/ci_run_compare.py --repo ParkJongHwan517/donga_oss 42810212598 42811375609
```
GitHub CLI(`gh`)가 로그인된 상태에서 실행합니다.
