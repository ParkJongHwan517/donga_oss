# Inner Source 도입 로드맵

**Inner Source**는 오픈소스의 개발 방식(공개된 코드, PR 기반 기여, 투명한 리뷰)을 **조직 내부**에 적용하는 방법입니다.
코드는 조직 밖에 공개하지 않지만, 조직 안에서는 팀 경계를 넘어 누구나 읽고 기여할 수 있게 합니다.

이 문서는 FIT 저장소에서 쓰고 있는 협업 장치를 조직에 확장한다고 가정하고 쓴 로드맵입니다.

## 1. 왜 도입하는가

| 문제 | Inner Source가 주는 효과 |
|---|---|
| 팀마다 비슷한 코드를 중복 개발 | 공용 컴포넌트를 찾아 재사용 |
| 다른 팀 코드의 작은 수정에도 요청과 대기가 필요 | 직접 PR을 보내 기여 |
| 지식이 특정 개인에게 몰림 | 문서와 코드 리뷰로 지식 공유 |
| 신규 입사자의 온보딩이 느림 | README, Wiki, ADR로 맥락 제공 |

## 2. 오픈소스와 Inner Source의 차이

| 항목 | 오픈소스 | Inner Source |
|---|---|---|
| 공개 범위 | 전 세계 | 조직 내부 |
| 기여자 | 불특정 다수 | 사내 구성원 |
| 동기 | 자율, 명성, 사용 필요 | 업무 목표, 평가, 재사용 |
| 라이선스 | OSI 승인 라이선스 | 사내 이용 조건 (외부 배포 시 별도 검토) |
| 리스크 | 보안·평판 | 보안 등급, 접근 권한, 책임 소재 |

## 3. 도입 원칙
1. **기본은 공개**: 민감 정보가 아니면 조직 안에서 읽을 수 있게 둔다.
2. **기여는 PR로**: 변경은 리뷰를 거쳐 병합한다.
3. **문서가 먼저**: 기여자가 질문 없이 시작할 수 있게 README와 CONTRIBUTING을 갖춘다.
4. **신뢰 기반 유지보수**: 프로젝트마다 Trusted Committer(핵심 메인테이너)를 둔다.
5. **측정과 개선**: 기여 수, 리뷰 시간, 재사용 횟수를 확인한다.

## 4. 역할

| 역할 | 책임 |
|---|---|
| 스폰서(경영진/팀장) | 시간과 평가에서 기여를 인정, 방향 지지 |
| Trusted Committer | 기여 리뷰·병합, 로드맵 관리, 기여자 안내 |
| 기여자 | 이슈, PR 작성, 가이드 준수 |
| 플랫폼/보안 담당 | 접근 권한, 비밀정보 스캔, 라이선스 점검 |
| 커뮤니티 매니저 | 문서 점검, 교육, 사례 공유 |

## 5. 단계별 로드맵 (12개월)

### 0단계: 진단 (1~2개월)
- 중복 개발이 많은 영역과 협업 병목을 조사한다.
- 파일럿 후보 프로젝트와 스폰서를 정한다.
- 접근 권한, 보안 등급, 사내 라이선스 정책을 확인한다.
- **산출물**: 현황 진단서, 파일럿 후보 목록

### 1단계: 파일럿 (3~5개월)
- 후보 중 1~2개 프로젝트를 선정한다.
- 기본 문서 세트를 갖춘다: `README`, `CONTRIBUTING`, `CODE_OF_CONDUCT`, `LICENSE`, 이슈·PR 템플릿, `CODEOWNERS`
- 브랜치 전략, Conventional Commits, PR 리뷰 규칙([MUST]/[SHOULD])을 적용한다.
- 자동 응답, SLA 알림, 주간 요약 같은 자동화를 붙인다.
- Discussions나 사내 메신저 채널을 열고, 큰 변경은 RFC로 논의해 ADR로 기록한다.
- **산출물**: 파일럿 저장소, 운영 가이드, 첫 외부 팀 기여 사례

### 2단계: 확산 (6~9개월)
- 파일럿 결과를 공유하고 대상 프로젝트를 5~10개로 늘린다.
- 공용 템플릿 저장소를 만든다.
- Trusted Committer 교육과 기여자 온보딩 세션을 연다.
- 사내 검색 가능한 프로젝트 카탈로그를 만든다.
- 평가 제도에 기여를 반영하는 방안을 논의한다.
- **산출물**: 템플릿 저장소, 프로젝트 카탈로그, 교육 자료

### 3단계: 정착 (10~12개월)
- 지표를 정기 보고하고 규칙을 개선한다.
- 커뮤니티 매니저 역할을 공식화한다.
- 우수 기여 사례를 공유하고 인정한다.
- 외부 오픈소스로 전환할 후보를 검토한다.
- **산출물**: 운영 보고서, 개선된 가이드

## 6. 성과 지표

| 지표 | 의미 | 측정 방법 |
|---|---|---|
| 팀 간 PR 수 | 협업 확산 정도 | PR 작성자와 저장소 소유 팀 비교 |
| 첫 응답 시간(SLA) | 기여자 경험 | 이슈/PR 생성 후 첫 댓글까지의 시간 (`sla-tracker.yml`) |
| PR 리드타임 | 개발 흐름 | 생성~병합 시간 (`metrics.yml`) |
| 재사용 횟수 | 중복 감소 | 공용 컴포넌트 의존 프로젝트 수 |
| 외부 기여자 수 | 참여 폭 | 소유 팀 외 구성원의 커밋 수 |
| 온보딩 시간 | 문서 품질 | 신규 인원의 첫 PR까지 걸린 시간 |

이 저장소의 `weekly-summary.yml`과 DORA 대시보드는 위 지표 중 일부를 자동으로 수집하는 초안입니다.

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 기여할 시간이 없다 | 스폰서가 업무 시간과 평가에서 기여를 인정 |
| 리뷰 병목, 메인테이너 과부하 | Trusted Committer 복수 지정, 리뷰 SLA 설정 |
| 품질 저하 | 리뷰 규칙, CI 테스트, 브랜치 보호 규칙 |
| 보안·기밀 유출 | 접근 권한 분리, 비밀정보 스캔, `.env` 커밋 금지 교육 |
| 문서 방치 | 문서도 PR로 관리하고 정기 점검 |
| 라이선스 오염 | 외부 코드 도입 전 라이선스 확인, 의존성 점검 |
| 문화 저항 | 파일럿 성공 사례 공유, 작은 기여부터 시작 |

## 8. 라이선스 정책 (조직 내부)
- 내부 코드에도 `LICENSE` 또는 사내 이용 조건 문서를 둔다.
- 외부 오픈소스를 쓸 때는 [라이선스 비교](license-comparison.md)의 기준으로 허용 목록(MIT, BSD, Apache-2.0 등)을 정하고, 카피레프트 라이선스는 사전 검토를 거친다.
- 외부로 공개하거나 배포할 가능성이 있는 코드는 처음부터 허용형 라이선스와 호환되도록 관리한다.

| 로드맵 요소 | 이 저장소의 현재 자료 |
