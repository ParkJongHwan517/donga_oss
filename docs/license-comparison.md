## 1. 한눈에 비교

| 라이선스 | 유형 | 소스 공개 의무 | 특허 조항 | 상업적 이용 | 대표 사례 |
|---|---|---|---|---|---|
| **MIT** | 허용형 | 없음 (저작권·라이선스 고지만 유지) | 명시 없음 | 가능 | React, Chart.js |
| **BSD-3-Clause** | 허용형 | 없음 (고지 유지, 이름 사용 제한) | 명시 없음 | 가능 | Django, Uvicorn |
| **Apache-2.0** | 허용형 | 없음 (고지·변경 표시, NOTICE 유지) | **명시적 특허 허여** | 가능 | Kubernetes |
| **MPL-2.0** | 약한 카피레프트 | **수정한 파일**만 공개 | 있음 | 가능 | Firefox |
| **LGPL-3.0** | 약한 카피레프트 | 라이브러리 수정분 공개 | 있음 | 가능 | 여러 공유 라이브러리 |
| **GPL-3.0** | 강한 카피레프트 | 배포하는 파생물 전체를 같은 조건으로 공개 | 있음 | 가능 (조건 준수) | GNU 도구들 |
| **AGPL-3.0** | 네트워크 카피레프트 | 네트워크로 서비스만 해도 소스 제공 | 있음 | 가능 (조건 준수) | 일부 서버 소프트웨어 |

> 카피레프트(copyleft): 파생물을 배포할 때 같은 라이선스로 공개하도록 요구하는 성질입니다.

## 2. 핵심 차이

### 허용형 (MIT, BSD, Apache-2.0)
- 코드를 가져다 쓰고 수정해 비공개 제품에 넣어도 됩니다.
- 요구사항은 저작권 고지와 라이선스 사본 유지 정도입니다.
- **MIT**는 문장이 가장 짧고 단순합니다. 특허에 대한 언급이 없습니다.
- **Apache-2.0**은 기여자가 특허 사용권을 함께 허여하고, 특허 소송을 걸면 그 권리가 종료되는 조항이 있습니다. 기업이 참여하는 프로젝트에서 선호됩니다.
- **BSD-3**은 MIT와 비슷하지만, 이름을 광고에 쓰는 것을 제한하는 조항이 있습니다.

### 카피레프트 (MPL, LGPL, GPL, AGPL)
- 개방성이 파생물까지 이어지도록 강제합니다.
- **MPL-2.0**은 파일 단위, **LGPL**은 라이브러리 단위, **GPL**은 프로그램 전체로 범위가 넓어집니다.
- **AGPL**은 배포하지 않고 서버로 서비스만 하는 경우에도 소스 제공 의무가 생깁니다.

## 3. 선택 기준 (질문 순서)

| 질문 | 예 | 아니오 |
|---|---|---|
| 1. 누구나 자유롭게, 제약 없이 쓰게 하고 싶은가? | 허용형 (2번으로) | 카피레프트 (4번으로) |
| 2. 특허 문제를 명시적으로 다뤄야 하는가? (기업 기여, 특허 위험) | **Apache-2.0** | 3번으로 |
| 3. 최대한 단순한 문구를 원하는가? | **MIT** | BSD-3 |
| 4. 수정사항이 반드시 공개되기를 원하는가? 범위는? | 파일: MPL / 라이브러리: LGPL / 전체: GPL | |
| 5. 서버로만 서비스하는 경우도 공개를 요구하는가? | AGPL | GPL |

추가로 확인할 것은 아래와 같습니다.
- **의존성 호환성**: 쓰는 라이브러리의 라이선스와 충돌하지 않는가. 예를 들어 GPL 코드를 포함하면 전체를 GPL로 배포해야 할 수 있습니다.
- **상업화 계획**: 나중에 비공개 제품이나 유료 서비스로 바꿀 가능성이 있는가.
- **기여자 기대**: 참여자가 어떤 조건을 기대하는가. 기여 내용은 보통 프로젝트 라이선스로 배포됩니다.
- **조직 정책**: 소속 기관이 허용하는 라이선스 목록이 있는가.

## 4. FIT 프로젝트의 선택: MIT

| 판단 요소 | 내용 |
|---|---|
| 성격 | 학습용 개인 프로젝트. 누구나 참고하고 가져다 쓸 수 있게 하는 것이 목적 |
| 의존성 | FastAPI(MIT), Supabase 클라이언트(MIT), Uvicorn·python-dotenv(BSD-3), Chart.js(MIT). 모두 허용형이라 MIT와 호환 |
| 특허 | 알고리즘 특허 이슈가 없고 기업 기여자도 없어 Apache-2.0의 특허 조항이 꼭 필요하지 않음 |
| 단순성 | MIT는 문구가 짧아 이해하고 지키기 쉬움 |
| 향후 확장 | 상업 서비스나 비공개 확장으로 바꿔도 라이선스 제약이 거의 없음 |

**결론**: 단순함과 확산을 우선해 MIT를 선택했습니다.
**다시 검토할 조건**: 기업 기여자가 참여해 특허가 쟁점이 되면 Apache-2.0을, 수정사항 환원을 강제하고 싶으면 MPL-2.0이나 GPL 계열을 검토합니다.
